Onde estamos hoje

O site mostra um checkout, mas ainda não cobra de verdade

As telas de pagamento já existem e estão bonitas — Pix, cartão, finalização. Mas por baixo, nenhum valor é cobrado: é uma simulação visual para validar a experiência. Para a barbearia receber online, falta o "encanamento" que conecta o site a um meio de pagamento real.

⚠️

Tradução simples

Hoje, quando o cliente clica em "pagar", a tela espera 2 segundos e mostra "sucesso" — mas o dinheiro não entra. Nenhuma assinatura do Clube é cobrada de fato. É como uma maquininha de demonstração: aperta os botões, mas não processa.

O que o cliente vai poder pagar

Três frentes de pagamento

Cada uma resolve uma dor diferente do negócio. Podem ser implementadas em sequência — a base técnica é a mesma para as três.

1

Pix no checkout

Cliente compra um produto ou plano avulso, gera um QR Code de verdade e a confirmação aparece sozinha na tela assim que ele paga.

Pix instantâneo
2

Assinatura do Clube

Cobrança mensal automática no cartão. É a receita previsível do negócio — o cliente assina uma vez e a renovação acontece todo mês sem intervenção.

Recorrência
3

Antifalta inteligente

Cliente fiel agenda normal, sem pagar antes. Quando alguém falta, o barbeiro marca o no-show — e só esse cliente passa a precisar pré-pagar para agendar de novo. Pune o caloteiro, não o cliente bom.

Bloqueio por reincidência

Integração com a operação

Nada de planilha paralela. Todo pagamento confirmado no site é lançado automaticamente no financeiro do painel admin, com a mesma classificação de forma (Pix, cartão) que a barbearia já usa hoje no balcão.

→

Confirmou no site

→

Lança no caixa

Entrada criada automaticamente no financeiro — sem digitação manual.

✓

Em detalhe · ferramenta antifalta

Como o antifalta vai funcionar

Decisão da equipe: não é cobrança antecipada para todo mundo — isso geraria atrito com o cliente fiel. O pré-pagamento é uma trava por reincidência, acionada pelo próprio barbeiro só contra quem falta.

👤 Cliente fiel — sem fricção

Agenda normalmente, escolhe a forma de pagamento e paga no balcão como sempre. Nunca é obrigado a pagar antes. A experiência dele não muda.

🚫 Cliente que falta — trava ativa

Depois de faltar (no-show marcado pelo barbeiro), ao tentar agendar de novo ele precisa pré-pagar para confirmar. Volta a ter benefício do balcão quando voltar a honrar os horários.

1

Cliente falta

Não aparece no horário marcado.

2

Barbeiro marca no-show

Um clique na agenda do painel admin registra a falta.

3

Contador sobe

O cadastro do cliente acumula as faltas.

4

Atingiu o limite

A partir de N faltas, ele entra em "exige pré-pagamento".

5

Próximo agendamento

Só esse cliente vê a cobrança obrigatória para confirmar.

🗣️

Pra fechar na reunião

Quantas faltas disparam a trava? O pré-pagamento é o valor cheio do serviço ou só uma parte (ex.: 30%)? O barbeiro pode "perdoar" e zerar o contador de um cliente? — são os pontos em aberto.

Decisão técnica · meio de pagamento

Por onde processar (comparativo)

Precisamos escolher um provedor de pagamento. Todos cobram uma taxa por transação. O sistema é construído de forma que trocar de provedor depois seja barato — mas começar com a escolha certa evita retrabalho.

Para o time técnico

Como funciona por baixo

A confirmação não depende do navegador do cliente: o provedor avisa nosso back-end via webhook, que é a fonte da verdade do status. O front apenas reflete o que está no Firestore em tempo real.

Cliente · Landing
Escolhe forma de pagamento
Recebe QR Pix / brick de cartão
Tela "aguardando" → ouve o status via onSnapshot
Nosso back · API routes
POST /api/pagamentos/criar
POST /api/pagamentos/webhook
Coleção pagamentos (Firestore) = fonte da verdade
Provedor (MP / Asaas)
Cria cobrança Pix / cartão / assinatura
Confirma pagamento → dispara webhook
🔒

Idempotência + assinatura: o webhook valida a assinatura do provedor e marca lancadoNoCaixa para não duplicar lançamento se o evento repetir. O cartão é tokenizado no SDK do provedor — nunca toca o nosso front.

O que muda no código atual

ProductCheckout / PlanCheckout: troca o setTimeout fake por chamada real + listener.
usePaymentMethod: deixa de coletar cartão (vira seletor + status).
PaymentMethodFields: QR placeholder → QR real da API.

Ponte com o caixa (domínio do Vitor)

No webhook, ao confirmar pago: checa idempotência → lança entrada no financeiro do admin (mesmo vocabulário de forma) → marca como lançado. O formato exato do lançamento precisa ser validado pelo Vitor.
