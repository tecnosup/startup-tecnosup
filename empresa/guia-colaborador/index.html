    Sua hierarquia: colaborador, não owner

    Saber exatamente onde sua autonomia começa e onde ela para — e por que a linha está onde está.

    Como isso funciona na prática

    Você não fica bloqueado por não ter acesso — você fica protegido. Seu trabalho termina num PR verde, com roteiro de teste escrito. Quem tem a chave aperta o botão. Se algo que você precisa está do outro lado da linha, o caminho é: descreva o que precisa e por quê, no PR ou no chat. Não invente contorno, não peça a chave "só dessa vez", não rode comando com credencial que alguém colou no chat.

    Segredo — regra absoluta

    Nenhuma credencial aparece neste guia e nunca vai aparecer. Em 17/06/2026 o conteúdo de um JSON de service account do Firebase foi ecoado dentro de um chat durante uma configuração de .env.local. A chave dava acesso total ao Firestore do cliente. Resultado: a service account inteira teve que ser excluída no Google Cloud, o que invalidou todas as chaves — inclusive a do outro dev, que passou dias com cinco rotas de API quebradas na máquina dele.

    Ao lidar com credencial: passe o caminho do arquivo, nunca o conteúdo.

    Incidente · 08/07/2026 O dev local apontava para o Firebase de produção e estourou a cota do cliente

    O .env.local do Ortega apontava para o mesmo banco que a barbearia usava ao vivo. Rodar npm run dev, typecheck e curls de teste consumia cota de leitura do banco real.

    No dia 08/07 isso estourou o limite do plano gratuito: 8 RESOURCE_EXHAUSTED: Quota exceeded. Vários endpoints do admin passaram a devolver 500 no local.

    O sintoma que confunde: no navegador o erro aparece como Failed to execute 'json' on 'Response': Unexpected end of JSON input, porque fetch(...).then(r => r.json()) sem checar r.ok estoura quando o 500 vem com corpo vazio. Você vai caçar bug de parsing e o problema é cota. Sempre cheque r.ok.

    Resolução: projeto Firebase separado só para desenvolvimento. São 9 chaves que mudam — as 6 NEXT_PUBLIC_FIREBASE_* e as 3 FIREBASE_ADMIN_*. As demais podem ficar iguais.

    Ferramentas específicas desta operação

    Duas que custam tempo se você não souber

    Ler PDF (manual de marca do cliente): não há poppler/pdftoppm nas máquinas. Use Python + pymupdf: fitz renderiza páginas com page.get_pixmap(dpi=150) e extrai as imagens embutidas em alta resolução com doc.extract_image(xref). Numa tentativa anterior o manual foi lido só pelos PNGs soltos e o sistema tipográfico inteiro saiu errado — o PDF é a autoridade da marca.

    Screenshot mobile de verdade: chrome --headless --window-size=390,844 mente. No Windows a largura de layout não desce abaixo de ~504px, então as media queries respondem como tablet e você vai depurar um bug de responsividade que não existe. O caminho certo é CDP: --remote-debugging-port + --remote-allow-origins=* (sem essa flag o handshake dá 403), conectar via websocket e chamar Emulation.setDeviceMetricsOverride.

    A forma de uma rota admin

    // src/app/api/admin/itens/route.ts
export const dynamic = "force-dynamic";   // obrigatório em rota admin

export async function POST(req: Request) {
  // 1. sessão SEMPRE primeiro — antes de ler o corpo
  const user = await getSessionUser();
  if (!user) return NextResponse.json({ erro: "nao autorizado" }, { status: 401 });

  // 2. valide a entrada com Zod. nunca confie no front.
  const parsed = ItemSchema.safeParse(await req.json());
  if (!parsed.success)
    return NextResponse.json({ erro: parsed.error.issues[0].message }, { status: 400 });

  // 3. Firestore rejeita undefined — limpe antes de gravar
  const dados = semUndefined(parsed.data);

  // 4. a regra de negócio vive em lib/, não aqui
  const id = await criarItem(dados);

  // 5. toda mutação de admin gera auditoria
  await registrarAuditoria(user, "item.create", id);

  return NextResponse.json({ ok: true, id });
}
    Cinco linhas que sempre estão lá
    • export const dynamic = "force-dynamic" em toda rota e layout do admin.
    • credentials: "include" em todo fetch do admin, senão o cookie não vai.
    • Firestore rejeita undefined — filtre os campos antes de .add() / .update().
    • getAdminDb() é chamado por request, nunca guardado em singleton.
    • orderBy duplo exige índice composto. Ordene por um campo e faça o segundo sort em memória.

    Modelagem no Firestore

    • Desnormalize o que a tela lê junto. O agendamento guarda barbeiroId e barbeiroNome. Uma leitura em vez de duas.
    • Guarde o ID, não só o rótulo. Caso real: o modelo Agendamento guardava o nome do serviço mas não o servicoId. Resultado: a tela de comissões não conseguiu calcular comissão por serviço, e a feature ficou bloqueada por uma decisão de modelagem tomada meses antes. Nome é para exibir; ID é para calcular. Guarde os dois.

    Fig. 04.1 — O bug de 14/07 desenhado. Com 10 min gravados, o intervalo do Clezio encosta mas não sobrepõe: o site ofereceu 13:30 corretamente, segundo o dado que tinha. A lógica estava certa; o dado estava errado.
    Incidente · 14/07/2026 Dois agendamentos sobrepostos no mesmo barbeiro — e as quatro hipóteses erradas

    As hipóteses levantadas na hora — todas refutadas depois:

    • "Falta validação server-side de conflito" — é um fato técnico verdadeiro, mas não causou este caso.
    • "Race condition / cache velho" — os dois agendamentos foram criados com 1h42 de diferença.
    • "O cliente escolheu sobrancelha primeiro e corte depois" — o fluxo público escolhe tudo no passo 1.
    • "Status pendente não ocupa slot" — pendente sempre ocupou; a API só ignora cancelado.

    A causa real, encontrada lendo os dois documentos em produção: o serviço "Cabelo na Tesoura + Barba" foi cadastrado sem duração. resolverDuracaoMin(svc, fallback) devolve o fallback quando o serviço não tem duração — e o front passava o passo da grade (5 min) como fallback. O serviço sem duração virou 5 minutos silenciosamente, e o combo de uma hora foi gravado como 10.

    O que resolveu: (1) cadastrar a duração real dos serviços faltantes — mata o caso na hora; (2) tornar duração obrigatória no cadastro, no cliente e no servidor.

    A lição: um fallback silencioso é uma bomba-relógio. Se um campo é essencial para o cálculo, ele é obrigatório na entrada — não tem default esperto que salve.

    3 · Remover a ambiguidade é melhor que consertar a ambiguidade

    Na mesma investigação apareceu a raiz da divergência: a opção "qualquer barbeiro disponível" (barbeiroId = null). Nesse fluxo os agendamentos de todos os barbeiros eram somados num conjunto único, então um horário sumia mesmo com outro barbeiro livre.

    Dava para consertar a semântica. A decisão foi remover a opção: barbeiro virou obrigatório nas três telas de escolha. Menos superfície, menos estado ambíguo. E o backend nem mudou — nunca houve atribuição automática.

    Como aplicar

    Quando uma feature existe mas ninguém consegue explicar o comportamento correto dela em uma frase, a pergunta certa não é "como conserto?" — é "isso precisa existir?". Traga a proposta de remoção com o argumento. Remover é decisão de produto: você propõe, o Abraão decide.

    4 · Ocultar, não deletar

    Quando o cliente ainda não decidiu como uma parte do sistema vai funcionar, ela sai da frente do usuário mas fica no repositório:

    Ao esconder uma feature, mapeie TODAS as superfícies

    Landing · navbar desktop · navbar mobile (hamburger) · rotas diretas (middleware redireciona) · botões dentro de outras telas · abas do admin. Esquecer uma é deixar um caminho aberto para uma tela quebrada.

    5 · Decidir antes de codar

    No Ortega, o checkout de plano e de produto ficou meses como setTimeout(2200) → ID aleatório → tela de sucesso. Nada era cobrado, o Pix era um QR estático, e o código parecia pronto.

    Quando chegou a hora de fazer pagamento de verdade, a arquitetura foi desenhada agnóstica de gateway e aprovada antes de uma linha ser escrita: coleção pagamentos como fonte da verdade do status, rota de criação, webhook (é ele que torna o pagamento real), front reativo por onSnapshot no lugar do setTimeout, e a ponte com o caixa.

    Regra de escopo

    Não escolha gateway, biblioteca de pagamento, provedor de e-mail ou serviço pago sozinho. Traga duas opções com trade-off. Escolha de fornecedor é decisão de negócio — tem custo, contrato e titularidade no nome do cliente.

    Segurança: o servidor decide, sempre

    O modelo de auth em camadas, o que é proteção de verdade e o que é só enfeite de UI.

    Endpoints públicos

    Caso real · o que quase foi feito errado

    Surgiu a ideia de deixar o cliente cancelar o próprio agendamento pelo fluxo público. O caminho preguiçoso seria expor o PATCH /api/agendamentos/[id] que já existe e já faz tudo.

    Por que é um furo: o ID vaza fácil pela URL e pelo sessionStorage. Qualquer terceiro cancelaria agendamento alheio.

    A forma certa: endpoint dedicado POST /api/publico/agendamentos/[id]/cancelar que valida posse (o telefone informado bate com o do agendamento) e janela de tempo (só até X horas antes). Endpoint público faz uma coisa só, com validação explícita — nunca reaproveita o endpoint poderoso do admin.

    Dívida de segurança conhecida — não repita o padrão

    Num dos projetos, o telefone é a única credencial do cliente: quem souber o número lista e cancela os agendamentos alheios. A raiz é estrutural — não existe entidade "cliente" no banco. As coleções são barbers, services, products, appointments, comandas… e o cliente só existe como customerPhone dentro de cada agendamento. Por isso a assinatura não tem dono e o bloqueio por reincidência não tem onde morar.

    A lição: identidade é entidade. Se um ator do sistema tem histórico, direitos ou estado, ele precisa de coleção própria — não de um campo string espalhado.

    PCI — por que cartão não passa por nós

    Custo e performance: o Firestore cobra por documento lido

    A área que mais derrubou sistema nosso. Se você entender só uma etapa técnica deste manual, que seja esta.

    O volume de leitura nunca foi proporcional ao movimento real da barbearia. Todo o custo era overhead de código.

    1. O Firestore cobra por documento lido, não por requisição. Uma query que devolve 1.000 documentos custa 1.000 leituras, mesmo que você use só a contagem.
    2. O plano gratuito não desacelera ao bater o limite — ele para. São 50 mil leituras/dia; ao estourar, tudo devolve RESOURCE_EXHAUSTED até a meia-noite do Pacífico. O sistema cai na cara do cliente.

    A descoberta mais instrutiva

    7.272 leituras numa coleção de 136 documentos

    Na tela de Agendamentos, dataSelecionada estava na lista de dependências de um único carregar() que buscava agendamentos + fechamentos + slots juntos. Mas só os slots dependem do dia escolhido.

    A pergunta antes de escrever uma query

    "Isso cresce com o histórico?" Uma query de "últimos 30 dias" dentro de um setInterval hoje lê 35 documentos e daqui a seis meses lê 400. Não é se vai estourar — é quando. Se cresce e roda em loop, o design está errado, mesmo que os números de hoje estejam bons.

    Armadilha de diagnóstico

    A tela Query Insights em "Latência (ms)" não responde sobre custo de cota — mostra queries lentas, não queries que leem muito. Uma coleção pode sumir do topo por latência (é rápida) e continuar sendo o maior custo. Para custo, use a quebra por coleção com tipo de carga em operações/documentos.

    Billing é preventivo, não reativo

    Ativar o plano pago depois de bloqueado não é imediato — propaga em minutos com o cliente no chão. Por isso o billing é ativado na entrega, com o cartão do cliente, mais alerta de orçamento. O plano pago não cobra nada dentro da cota gratuita. Isso está em cláusula de contrato: custos de infra são 100% do contratante, e a Tecnosup se obriga a manter o sistema dentro da cota gratuita por design — obrigação de meio, não de resultado.

    Por que acontece

    Next.js 16 transpila para Chrome 111 / Safari 16.4 por padrão, mas respeita o browserslist do package.json.

    Tailwind CSS 4 tem os alvos fixos dentro do pacote (safari 16.4, chrome 111, firefox 128) e ignora o browserslist completamente. Não tem config que resolva.

    Migrar Tailwind 4 → 3Estrutural: o v3 nunca gerou oklch/color-mix/@propertyAlto, mas definitivo

    Um remendo com @supports not (color: color-mix(...)) já foi tentado e não resolveu: cobre só uma lista manual de seletores e não cobre @property de forma alguma — que é usado nas mecânicas internas do próprio framework. Testado no iPhone 7 real: o problema persistiu.

    Se você migrar v4 → v3, essa é a pegadinha

    O v4 aceita qualquer porcentagem de opacidade (/4, /15, /35, /98). O v3 só tem escala fixa (0, 5, 10, 20, 25, 30…). Classes fora da escala são silenciosamente ignoradas — a cor sai 100% opaca. Números que eram marca d'água atrás dos cards apareceram dourado chapado.

    Correção: estender theme.extend.opacity no tailwind.config.js com os valores usados. Resolve todos de uma vez sem tocar componente. Cuidado com /08 — zero à esquerda é ambíguo no parser do v3; normalize para /8.

    Critério objetivo de sucesso: o CSS gerado tem 0 oklch, 0 color-mix, 0 @property.

    Git e GitHub: o fluxo é obrigatório

    Como o trabalho circula entre pessoas sem ninguém pisar no pé do outro.

    main
    merge · produção
    dev
    PR + revisão ↑
    feat/erick-…
    parte de dev ↑
    Fig. 08.1 — O único caminho: a branch nasce de dev atualizada, volta para dev por PR revisado, e só então dev sobe para main. Você trabalha na faixa azul; as duas de cima não são suas.

    O ciclo completo

    # 1. SEMPRE comece sincronizando. sem exceção.
git checkout dev && git pull origin dev

# 2. branch da sua área
git checkout -b feat/erick-produtos

# 3. trabalhe e commite normalmente
git add -A
git commit -m "feat: filtro de categoria na listagem de produtos"

# 4. antes de abrir o PR, sincronize de novo
git checkout dev && git pull origin dev
git checkout feat/erick-produtos
git merge dev            # resolva conflito AQUI, não no PR

# 5. suba e abra PR para dev
git push -u origin feat/erick-produtos
    Proibições
    • Nunca git push --force. Em nenhuma branch, em nenhuma circunstância.
    • Nunca commite direto em dev ou main — mesmo que o git deixe.
    • Nunca abra branch a partir de main. Sempre de dev atualizada.
    • Nunca commite .env*, JSON de service account, ou pasta de assets pesados.
    • Nunca reescreva histórico de branch compartilhada.
    Sinal de que a dev está desatualizada

    Quando um PR entra direto na main sem voltar para a dev, quem branchar da dev parte de código velho. Já aconteceu de a dev ficar 10 commits atrás da main. Comece a sessão checando:

    git fetch --all
git rev-list --count origin/dev..origin/main
# 0 = tudo certo. qualquer outro número = avise antes de branchar.

    Convenção de commit

    feat:     nova funcionalidade
fix:      correção de bug
refactor: mudança sem impacto de comportamento
chore:    build, deps, config
perf:     otimização
style:    só visual/formatação

    Divisão de áreas — e o arquivo que dá conflito

    Cada dev tem um território para não haver conflito de merge. A divisão é organizacional, não um limite de atuação: você pode ler e propor mudança em qualquer parte, mas antes de mexer na área de outro, avise.

    Arquivo compartilhado

    src/components/admin/AdminNav.tsx é o único arquivo com risco real de conflito entre áreas. Qualquer alteração ali precisa ser comunicada antes de você editar. Se cada um adicionar um item de menu na sua branch, o merge quebra.

    Revisão de PR

    • O autor não se auto-aprova. Sempre outro par de olhos.
    • Revisor roda a branch localmente, com o .env.local de teste. nunca no preview — motivo na etapa 09.
    • O PR traz roteiro de teste: o que clicar e o que deve acontecer.
    • Achou um bug real na revisão? Ótimo — foi assim que se pegou um agregador cujo mapa interno crescia sem limite e ia estourar o teto de 1 MiB por documento. Revisão pegou antes de produção.

    Duas pegadinhas de plataforma

    Windows é case-insensitive; o servidor é Linux

    Uma pasta em public/CORTES funciona na sua máquina e quebra em produção se o código pede /cortes/. Imagens somem só no ar. Confira o casing exato de todo path de asset.

    "Upar" significa local e remoto

    Quando pedirem para "upar" um trabalho, a expectativa é commit/merge e git push na branch remota correspondente. Parar no commit local já gerou a impressão de trabalho não feito.

    ⚠ Preview do Vercel aponta para o banco de PRODUÇÃO

    Todas as variáveis de Firebase estão marcadas para Production E Preview com o mesmo valor. Não existe valor separado só para Preview.

    Consequência: qualquer preview de dev ou de uma feature escreve no banco real do cliente. Mandar alguém "revisar no preview" é mandar essa pessoa mexer em produção — cadastrar produto, ajustar estoque, criar serviço, tudo cai no cliente.

    Por isso a revisão é local. git checkout feat/... && npm install && npm run dev com o .env.local de teste. Zero risco, zero configuração.

    Variáveis de ambiente não viajam

    Ao transferir um projeto Vercel de conta, as env vars não vão junto. Se ninguém repuser antes do primeiro deploy, o site quebra em runtime. Outra: projeto criado pela CLI nasce com framework: null e dá 404 em tudo, mesmo com build perfeito. Importar pelo dashboard detecta sozinho.

    Antes de pedir merge, seu PR precisa passar aqui

    Retrocompatibilidade — o padrão que salvou uma entrega

    Quando a duração numérica de serviço foi introduzida, os serviços e agendamentos antigos não tinham o campo. Em vez de exigir migração, o código usa o passo da grade como fallback: registros antigos ocupam um slot e não somem da agenda. O cliente nem percebeu a mudança de modelo.

    Sempre que adicionar campo a um documento que já existe em produção, responda no PR: o que acontece com os registros que não têm esse campo?

    Falha silenciosa é dívida

    Em duas telas do admin, handleDelete não dá feedback de erro: se o DELETE falha por rede, nada acontece na tela. O usuário acha que apagou. Isso está anotado como pendência há meses — não crie mais desses. Toda ação assíncrona tem três estados visíveis: carregando, sucesso, erro.

    Detalhe de custo: popup e confirm são client-side puros — zero leitura no banco. O que custa é o refetch depois da ação. Sempre que der, atualize em memória em vez de recarregar a lista inteira.

    11

    Cliente e escopo: onde o dev para e o negócio começa

    Reconhecer a decisão que não é sua — e o que nunca prometer.

    Decisão de produto não é decisão técnica. Quando a resposta depende de como o cliente quer tocar o negócio dele, a resposta não é sua.

    Exemplos reais de decisão que não era do dev

    • Cliente cancelar o próprio agendamento pelo site. Tecnicamente trivial. Mas o dono pode preferir que o cliente ligue — reagenda na conversa, mantém a relação. Self-service pode ser pior para o negócio dele.
    • Ferramenta antifalta. A proposta inicial era sinal antecipado obrigatório para todo agendamento. O sócio rejeitou: cria atrito para cliente bom. O conceito certo virou bloqueio por reincidência — o cliente agenda normal, o barbeiro marca a falta, e a partir de N faltas aquele cliente passa a ser obrigado a pré-pagar.
    • Assinatura manual entra em cobrança recorrente automática? Muda a complexidade da implementação inteira. Ficou parada esperando o cliente decidir — e a instrução foi explícita: preparar os dois cenários para apresentar, não implementar nenhum.
    Como se comportar

    Ao esbarrar numa dessas: pare, escreva os cenários com o trade-off de cada um, e devolva a decisão. Não crave o número (quantas faltas, quantas horas de antecedência, qual valor) sozinho. Deixar registrado "aguardando decisão" é entrega válida — implementar o palpite errado não é.

    O que nunca prometer

    Expectativa é contrato informal

    O desenvolvimento é personalizado, feito do zero com a cara da empresa até a entrega. Depois da entrega, toda feature nova é orçada e paga à parte. A mensalidade cobre operação — hospedagem, banco dedicado, suporte, backup, segurança — não features.

    Evite em qualquer texto, PR ou conversa: "evolução contínua", "novas funcionalidades no roadmap", "a gente vai melhorando".

    Produção real muda a régua

    A partir do momento em que um sistema tem clientes de verdade dentro, bug não é bug: é a operação de um negócio parada. Isso mudou o fluxo de trabalho da equipe inteira (etapa 04, princípio 6) e é a razão de existir de quase toda regra deste manual.

    Antes de qualquer alteração visível num sistema em produção: descreva o que vai mudar e confirme antes de aplicar. Especialmente se envolver Firestore ou regras de segurança.

    Ajuste visual: pergunte antes de chutar

    Quando alguém disser que algo "não ficou bom", pergunte exatamente o quê — a faixa? o logo? a posição? o tamanho? Chutar por print queima tentativas e paciência. Debater trinta segundos vale mais que três tentativas às cegas.
